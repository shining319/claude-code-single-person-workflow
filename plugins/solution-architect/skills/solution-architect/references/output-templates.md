## 12. 反模式清单与评审检查表

### 12.1 常见反模式

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 简历驱动的微服务 | 3 人团队 10 个服务，分布式复杂度远超收益 | 模块化单体 |
| 分布式单体 | 服务拆了但共享数据库、同步链式调用、必须一起发布 | 按领域拆分、独立数据、异步解耦 |
| 共享数据库跨服务写 | 耦合、无法独立演进 | 每服务拥有自己的数据，通过 API/事件交互 |
| 在 Serverless 函数里跑长任务/定时任务 | 超时、重复执行 | 队列 + 常驻 worker / 托管工作流 |
| 客户端做权限判断 | 可绕过 | 服务端强制鉴权 |
| JWT 存 localStorage 且长期有效 | XSS 窃取、无法撤销 | HttpOnly Cookie 会话或短期 JWT + 轮换 |
| 没有幂等的支付回调 | 重复入账/发货 | 幂等键 + 状态机 |
| 缓存无失效策略 | 数据不一致 | 明确 TTL 与失效时机 |
| 日志打印敏感信息 | 合规风险 | 结构化日志 + 脱敏 |
| 手工部署、无回滚 | 事故恢复慢 | CI/CD + 不可变镜像 + 一键回滚 |
| 没有备份恢复演练 | 备份不可用 | 定期演练 |
| 过早分库分表 | 复杂度爆炸 | 索引、缓存、读副本优先 |
| 盲目追新 | 生态不成熟、踩坑 | 核心链路用成熟技术，边缘尝试新技术 |
| 把 Next.js 当万能后端 | 复杂业务、长任务、多客户端时难以维护 | 业务变复杂后拆出独立 API 服务 |

### 12.2 架构评审检查表

- [ ] 需求与 NFR 是否量化？容量估算是否合理？
- [ ] 架构模式是否与团队规模、业务复杂度匹配？
- [ ] 单点故障有哪些？如何消除或接受？
- [ ] 数据一致性边界是否清晰？跨服务流程如何补偿？
- [ ] 认证授权是否在服务端统一实施？
- [ ] 外部依赖故障时如何降级？
- [ ] 扩展瓶颈在哪一层？下一步扩展方案是什么？
- [ ] 可观测性是否能在 5 分钟内定位问题？
- [ ] 部署是否自动化、可回滚？
- [ ] 合规要求（GDPR/PIPL/备案/PCI）是否覆盖？
- [ ] 成本是否在预算内？增长后成本曲线如何？
- [ ] 是否记录了关键决策的 ADR 与被否决方案？
